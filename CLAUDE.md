# Mazelight — неоновый лабиринт с уровнями

Мобильная игра-головоломка на Flutter + Flame. Этот файл — контекст проекта,
чтобы не объяснять концепцию заново в каждой новой сессии. План работы ведётся
по частям (см. "Порядок реализации" ниже) — не пытаться сделать всё сразу.

## Концепция

Пошаговая головоломка-лабиринт в тёмном неоновом стиле. Игрок ведёт фигуру
(круглая точка) от входа к выходу лабиринта. Уровни возрастающей сложности.

## Визуальный стиль

**Решение (пересмотрено):** отказались от чисто неонового минимализма в
пользу рескина под каменное подземелье с факелами (по референсу пользователя)
— тёмный фон, но стены/пол как текстурированные каменные блоки, а не тонкие
светящиеся линии. Детали см. в «Статус» ниже.

- Тёмный/чёрный фон
- Стены лабиринта — блоки-«кубики» вдоль рёбер клеток (сейчас плейсхолдер:
  плоская заливка с псевдо-3D тенью; позже — текстуры камня)
- Персонаж и спецклетки — сплошные цветные круги/сферы со свечением
- Пока БЕЗ факелов/анимаций/декора — это будет добавляться отдельным этапом
  вместе с реальными арт-ассетами

## Технический стек

- Flutter + пакет `flame` (^1.18.0) — **ещё не добавлен в pubspec.yaml**,
  сейчас в проекте только дефолтный Flutter-скаффолд
- Генерация лабиринта — чистый Dart-алгоритм, независим от Flame (важно для
  юнит-тестов на проходимость)
- Рендер сетки/стен/персонажа — через Flame-компоненты и Canvas API
- Состояние уровня/прогресса — SharedPreferences на первом этапе, без бэкенда

## Правила структуры кода

- Не больше 200 строк в одном файле — если файл разрастается, разбивать.
- Каждый компонент (Flame-компонент), виджет и метод/утилита — в отдельном
  файле, не собирать по несколько штук в одном месте.

## Механика по этапам прогрессии

**Уровни 1–5** (база):
- Поле 7x7, генерация — Recursive Backtracker или Prim's, гарантированно
  проходимый лабиринт, один вход и один выход
- Движение — **джойстик** (пересмотрено: изначально обсуждали D-pad кнопки,
  но при реализации персонажа/управления пользователь явно попросил
  джойстик под лабиринтом; свайп/тап из исходной идеи по-прежнему не
  используем)
- Победа — дойти до выхода
- Счётчик ходов и/или таймер → влияет на количество звёзд (1–3)
- Пока не добавляем: собираемые предметы, подсказки с лимитом, миникарта —
  сознательно отложено при обсуждении UI, не часть базовой механики

**Уровни 6–10**:
- Поле растёт (11x11+)
- Ловушки: шипы (откат к старту), телепорты (перенос в другую точку)

**Уровни 11+** (динамика, выбрать один из вариантов или оба):
- Часть стен сдвигается каждые N ходов
- Туман войны — видно поле только в радиусе 2–3 клеток от игрока

## Дополнительные механики (порядок добавления обсуждается отдельно)

- Ключи и двери: ключ нужного цвета открывает дверь того же цвета
- Враг-патруль: фиксированный маршрут либо преследование через BFS до игрока;
  столкновение = проигрыш/откат уровня
- Звёзды за скорость: 3 звезды за X ходов, 2 за Y, 1 за факт прохождения

## Генерация уровней — два режима, оба нужны

1. Процедурная генерация по seed = номер уровня (одинаковый лабиринт у всех
   игроков на уровне N)
2. Захардкоженные вручную лабиринты в JSON-формате сетки — для
   дизайнерских/сложных уровней

## Что сознательно НЕ делаем на первом этапе

- Онлайн-мультиплеер (интернет/Bluetooth) — отдельная задача поверх готовой
  логики уровней
- Монетизация/реклама
- Полноценный левел-эдитор с UI (только JSON для ручных уровней)

## Порядок реализации (делаем поэтапно, по одной части за раз)

1. Генератор лабиринта (чистая Dart-логика + тесты на проходимость)
2. Базовый рендер сетки + стен на Flame
3. Управление персонажем и детекция победы/поражения
4. Прогрессия уровней 1–5 + подсчёт звёзд
5. Ловушки (шипы, телепорты) и увеличение поля для уровней 6–10
6. Динамика (сдвиг стен или туман войны) для уровней 11+
7. Ключи/двери
8. Враг-патруль
9. (позже) мультиплеер

- **Этап 1 готов**: генератор лабиринта на `lib/maze/`:
  - `direction.dart` — `Direction` enum (north/east/south/west) с `opposite`,
    `dRow`, `dCol`
  - `grid_position.dart` — value-класс `GridPosition(row, col)` с `==`/`hashCode`
  - `maze_cell.dart` — `MazeCell` хранит `Set<Direction> walls` (какие стены
    ЕСТЬ; по умолчанию все 4, генератор убирает стены при прокладке прохода)
  - `maze.dart` — `Maze` (grid + `entrance`/`exit` как `GridPosition`),
    методы `cellAt`, `inBounds`, `canMove`
  - `maze_generator.dart` — `MazeGenerator(rows, cols, seed).generate()`,
    randomized Prim's (изначально был Recursive Backtracker, см. запись про
    смену алгоритма ниже), детерминирован по seed. Вход всегда (0,0), выход
    — противоположный угол (rows-1, cols-1)
  - Тесты: `test/maze/maze_generator_test.dart` — связность (BFS от входа
    покрывает все клетки), проходимость до выхода, "идеальность" лабиринта
    (ровно rows*cols-1 проходов, без циклов), детерминизм по seed, разные
    сиды → разные лабиринты, внешние стены не пробиваются, edge case 1x1
  - Всё проверено: `flutter test` и `flutter analyze` чистые
- **Этап 2 в процессе**: рендер борда на Flame, теперь с реальными
  текстурами (пользователь добавил PNG в `assets/images/`):
  - Flame добавлен в pubspec.yaml (`flame: ^1.18.0`, реально установилось 1.30.1)
  - `assets/images/floor.png` (1280x853, цельная каменная текстура пола) и
    `brick_1.png`..`brick_4.png` (варианты кирпичных блоков, разной формы —
    используются для стен) зарегистрированы в pubspec.yaml (`assets:
    - assets/images/`)
  - `lib/game/board/board_assets.dart` — `BoardAssets.load()`, грузит
    `Sprite`'ы через `Sprite.load()` (дефолтный префикс Flame `assets/images/`
    совпадает с папкой проекта, поэтому пути в коде — просто `floor.png`,
    `brick_1.png` и т.д.)
  - `lib/game/board/board_theme.dart` — теперь только `cellSize`,
    `wallThicknessRatio` (0.32 — подобран под «толщину» кирпичных спрайтов) и
    цвет фона; цветовые константы под плоскую заливку убраны, они больше не
    нужны
  - `lib/game/board/floor_painter.dart` — `paintFloorBackground()`: пол не
    тайлится по клеткам, а растягивается ОДНИМ вызовом на весь борд (исходная
    текстура уже читается как цельный пол, с тайлингом по клеткам была бы
    видна виньетка по краям картинки)
  - `lib/game/board/wall_sprite_painter.dart` — `paintBrickWall()`:
    **важно** — НЕ растягивает один спрайт на весь footprint (первая версия
    так делала, и все 4 разных по размеру кирпича визуально сплющивались в
    одну размазанную полосу — баг, на который указал пользователь). Вместо
    этого кладёт кирпичи в ряд встык (реальная кладка): каждый кирпич
    масштабируется РАВНОМЕРНО (высота = толщина стены, ширина — пропорционально
    своему аспекту), поэтому все 4 текстуры остаются узнаваемо разными по
    форме; ряд заполняется случайным (но seeded, т.е. стабильным между
    кадрами) порядком кирпичов, последний в ряду обрезается по ширине
    источника (`srcRect`), а не сжимается, если не влезает целиком. Для
    вертикальных стен — тот же поворот canvas на 90° вокруг центра footprint
  - `lib/game/board/maze_board_component.dart` — для каждого сегмента стены
    передаёт детерминированный seed (`_seedFor`, хэш от row/col/edgeSalt) в
    `paintBrickWall`, чтобы кладка была стабильной между перерисовками, но
    разной между сегментами
  - `lib/game/board/wall_shadow_painter.dart` — `paintWallShadow()` +
    `paintWallSideFace()`: эффект 3D/высоты стен. Конвенция фиксированного
    верхнего света (top-down), не зависит от ориентации стены
    (horizontal/rotated-vertical) — у каждого сегмента снизу рисуется тёмная
    сплошная «боковая грань» (`wallSideColor`, высота = `wallHeightRatio` от
    `cellSize`) + под ней мягкая размытая тень на полу (`MaskFilter.blur`)
  - **Важно**: `MazeBoardComponent.render()` рисует стены в 3 прохода по ВСЕМ
    сегментам сразу (сначала все тени, потом все боковые грани, потом все
    кирпичные кладки сверху) — не по одному сегменту за раз. Если тень/грань
    рисовать сразу за кладкой одного сегмента, тень соседней стены может
    случайно лечь поверх уже нарисованной кирпичной кладки другого сегмента и
    затемнить её
  - `lib/game/maze_game.dart` — `onLoad()` сначала ждёт `BoardAssets.load()`,
    потом создаёт `MazeBoardComponent(maze: maze, assets: assets)`
  - `lib/screens/maze_screen.dart` — временный экран с `GameWidget`,
    генерирует тестовый лабиринт 7x7 seed=1. Будет заменён на реальный
    level-flow позже
  - **Важно (грабли)**: компонент борда добавлять через `world.add(board)`,
    а не `add(board)` — иначе камера (`camera.viewfinder.visibleGameSize`/
    `position`/`anchor`) его не масштабирует и не центрирует (`add()` на
    саму игру кладёт компонент вне `world`, camera transform на него не
    действует)
  - Визуально проверено через `flutter run -d chrome` — пол и кирпичные
    стены рендерятся корректно, без ошибок в консоли

    `navigator.serviceWorker.getRegistrations().then(rs => rs.forEach(r => r.unregister()))`,

- **Персонаж + джойстик добавлены**:
  - `lib/game/player/player_component.dart` — `PlayerComponent`, зелёный
    шарик. Хранит `gridPosition` (текущая клетка) и плавно анимирует
    (`update()`, линейная интерполяция по скорости `_speed`) движение к
    соседней клетке через `moveTo(GridPosition)`; `isMoving` — идёт ли
    сейчас анимация. Рендер — через `player_ball_painter.dart`
    (`paintPlayerBall`, тот же паттерн отдельных paint-функций, что и у
    стен/пола: свечение + сплошной круг + блик)
  - `lib/game/controls/joystick_widget.dart` — `JoystickWidget`, обычный
    Flutter-виджет (НЕ Flame-компонент) с `GestureDetector`. Тянешь ручку —
    определяется `Direction` по углу (`offset.direction`, сектора по 90°) с
    мёртвой зоной `JoystickTheme.deadZone`; пока направление держится,
    каждые `JoystickTheme.stepInterval` (180мс) вызывается `onStep(direction)`
    через `Timer.periodic`. `lib/game/controls/joystick_theme.dart` — размеры/
    цвета/интервал отдельно, по аналогии с `BoardTheme`
  - `MazeGame.movePlayer(Direction)` (в `lib/game/maze_game.dart`) —
    единственное место, которое проверяет стены (`maze.canMove`); джойстик
    только "просит" шаг, движение молча игнорируется, если стена или если
    `player.isMoving` (анимация ещё не доехала) — так повторные шаги не
    накладываются друг на друга
  - **Важно**: джойстик — это Flutter-виджет ПОД `GameWidget` в `Column`
    (`lib/screens/maze_screen.dart`), а не Flame-компонент в `camera.viewport`.
    Так он физически лежит "снизу лабиринта", а не поверх канвы
  - `lib/game/controls/joystick_dock.dart` — `JoystickDock` оборачивает
    джойстик в полосу под лабиринтом (не чёрный фон `Scaffold` напрямую).
    Изначально фон был `floor.png` через `Image.asset`; пользователь потом
    сам поправил на сплошную заливку `BoardTheme.wallSideColor` — так и
    оставлено, не переделывать обратно на текстуру без явной просьбы
  - **Скорость шарика зависит от того, насколько отклонён джойстик**
    (запрошено пользователем отдельно после первой версии джойстика):
    - `JoystickWidget` (`lib/game/controls/joystick_widget.dart`) считает
      `intensity` (0..1: 0 — сразу за мёртвой зоной, 1 — до упора) и передаёт
      её вместе с `Direction` в `onStep` (тип колбэка теперь
      `JoystickStepCallback = void Function(Direction, double)`, а не
      `ValueChanged<Direction>`)
    - Пока направление удерживается, повтор шага — не фиксированный
      `Timer.periodic`, а самопланирующийся `Timer` (`_fireStep` вызывает сам
      себя через новый `Timer` каждый раз), с интервалом от
      `JoystickTheme.stepIntervalSlow` (480мс, слабое отклонение) до
      `stepIntervalFast` (110мс, до упора) — так интервал продолжает
      подстраиваться под `intensity`, даже если направление не меняется, а
      сила нажатия меняется прямо во время удержания
    - `MazeGame.movePlayer(Direction, double intensity)` переводит
      `intensity` в `speedFactor` (`_minSpeedFactor` 0.35 .. 1.0) и передаёт в
      `PlayerComponent.moveTo(target, speedFactor: ...)`; `PlayerComponent`
      хранит `_speedFactor` для текущего перегона и умножает на него
      `_baseSpeed` в `update()` — визуальный "накат" шарика к соседней клетке
      физически медленнее при лёгком отклонении ручки
  - Визуально проверено через `flutter run -d chrome`: перетаскивание ручки
    двигает шарик на соседнюю клетку и корректно останавливается у стен;
    ошибок в консоли нет

- **Генератор лабиринта сменён с Recursive Backtracker на randomized Prim's**
  (`lib/maze/maze_generator.dart`) — пользователь дошёл до 15 уровня и
  пожаловался, что лабиринты ощущаются как "один путь, который просто крутит
  по всей карте" (долго, но не сложно), и явно попросил лабиринты с
  несколькими путями, из которых только один ведёт к выходу. Recursive
  Backtracker (DFS, углубляется в одну ветку до конца) даёт именно такой
  эффект — длинные извилистые коридоры с редкими развилками. Prim's
  распространяет проходы одновременно от многих "фронтирных" клеток, поэтому
  даёт частые короткие тупики и развилки — по-прежнему идеальный лабиринт
  (ровно один путь к выходу, без циклов — тест на это не менялся и прошёл),
  просто с другим характером. Сам алгоритм: список `_WallCandidate`
  (`from`/`direction`/`to`) как "фронтир"; на каждом шаге случайно берём
  кандидата из фронтира (`random.nextInt(frontier.length)` +
  `removeAt`), пропускаем, если `to` уже в лабиринте, иначе прокладываем
  проход и добавляем фронтир новой клетки. Существующие тесты в
  `test/maze/maze_generator_test.dart` проверяют СВОЙСТВА лабиринта
  (связность, идеальность, детерминизм по seed, границы), а не конкретный
  алгоритм — прошли без изменений. Визуально проверено (временная подмена
  `home` на уровень 15/13×13): вместо одного длинного змеевидного коридора
  теперь много коротких тупиковых ответвлений
